Trade-off

Higher latency per batch, but predictable, low peak load — the right trade for a non-time-critical workload.

Problem

Still fetches every tender's detail page up front, even ones that will obviously get rejected.

Win

Clearly-irrelevant tenders never trigger a detail-page scrape at all — saves bandwidth and time.

Problem

The server is still blocked, waiting on the full LangGraph run to finish before it can move to the next batch.

Architecture evolution v1.3.0

Win

Architecture evolution v2.0.0

v5 — BullMQ for multi-site scheduling

feat: one scheduled background job per website
v1 naive loop
v2 serial calls
v3 lazy fetch
v4 add queue
v5 multi-site
v6 microservice

Why BullMQ, not more intervals

Latency still doesn't matter — priority stays low hardware/infra cost. BullMQ gives per-site scheduling without hardcoding a timer per website.

New problem

As sites are added, LangGraph's load grows much faster than everything else — it becomes the clear bottleneck while the rest of the system sits idle.

Architecture evolution v3.0.0 — current target

v6 — LangGraph as its own microservice

feat: extract LangGraph into a stateless, independently-scalable service
v1 naive loop
v2 serial calls
v3 lazy fetch
v4 add queue
v5 multi-site
v6 microservice

Why split

LangGraph is the only component under real scaling pressure — scale it alone instead of the whole stack.

Stays async

Same async communication as before, now with a second queue (tender-results) so LangGraph never needs to know who's consuming it.

Stateless by design

LangGraph service holds no state between jobs — easy to run N replicas behind the same queue.

Inside Service 2

The LangGraph state graph

Status lives on shared graph state. getDetailedPage is only visited when the ranker isn't confident from list data alone — the same lazy-fetch idea from v3, now expressed as a proper conditional edge.

Putting it together

End-to-end pipeline (current target, v6)

Only writer

NestJS remains the sole Postgres writer — LangGraph never touches the DB directly.

Fully async

Two queues, zero synchronous calls between the scraping side and the AI side.

Scales where it hurts

Add replicas of the LangGraph service under load — nothing else needs to change.
